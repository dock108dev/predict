### What the guard and retention implementation actually establish

`app/collection/data_runtime.py:resource_guard` checks
`pg_database_size(current_database()) >= 2,147,483,648`. It measures the whole
application database's physical allocation, including tables/indexes/TOAST and
other database files; it does not measure the cluster directory, WAL, live JSON
payload or only current rows. `current_storage_policy.sql_usage` is a different,
narrower preflight: public `current_*` tables plus its named latest/runtime tables
and current-owned sequences. For example, `pipeline_generation` and
`raw_aggregate_display` are outside that named subset but inside the fatal guard.
This mismatch is verified code behavior, not a measurement of their contribution.

Two recovery obstacles are established from control flow:

- Startup calls the fatal guard **before** migration/service startup. Therefore
  `DatabasePipeline.start` expiry and its 60-second expiry maintenance cannot run
  through an over-cap data-runtime startup. That maintenance expires current rows;
  it does not perform physical file compaction.
- `latest_board.publish` calls `grid_packet_store.cleanup` inside the publication
  transaction, before capacity validation. A later capacity rejection rolls back
  the deletes along with publication. Packet retention requires an expired
  180-second retirement grace, no current projection and no SQL read lease.
  `pipeline_generation.prune` runs from the financial child, retaining unfinished
  work and terminal history bounded by two hours/50,000 rows; it also cannot run
  through a refused runtime startup.

Ingress replaces current rows/native depth; publications replace latest rows and
create immutable leased Original packets. These are candidate write owners.
Logs retain repeated ingress advisory-lock timeouts and the final SQL-size guard;
they do not establish which table grew, whether vacuum was blocked, or whether
live bytes, dead tuples, indexes or obsolete packets dominate. **Responsible
incident write path and lifecycle cause remain unmeasured.** No live database size,
relation/index/TOAST bytes, live/dead row count, free space, cleanup eligibility,

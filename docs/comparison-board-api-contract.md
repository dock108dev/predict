# Saved-board API and update contract

`predict-comparison-board-1` is implemented in `app/dashboard/comparison_board.py`
and `comparison_board_api.py`, mounted by the database-mode `stored_games` router.
Ordinary Odds, EV, Arbs and saved Details use these endpoints.

## Read requests and meanings

| GET route | Result |
|---|---|
| `/api/boards/games` | `predict-board-catalog-1`, at most 200 NFL full-game winner occurrences, canonical game keys, original source members, participants, matching status and native alternative counts. Conflicting/unmatched occurrences retain separate source-local keys. No settings query. |
| `/api/boards/odds?game=KEY` | Original offered prices, server-formatted American equivalents and a separate named two-sided benchmark with original clocks, exact decisive probabilities and fair decimal prices. Native NO/Short retain their original participant/predicate. |
| `/api/boards/ev?game=KEY&filter=all` | Singles with exact shared financial metrics, funding, classification, model identity, dependency-local freshness and Details identity. Default `filter=positive` selects the financial owner's `main_positive_eligible`. |
| `/api/boards/arbs?game=KEY&filter=all` | Opposing pairs, both original selections/prices/venues, actual final modeled quantities/units, acquisition/upfront fees, shared funding/residual/buffer, complete/conditional EV, decisive/all-state margins and adverse/unknown outcomes. Default `positive` selects complete modeled minimum positives. `hedges` selects rule-sensitive positives. |
| `/api/boards/details?game=KEY&result_id=RID&quote=QID` | Exact selected saved single, full financial reconciliation, inputs/profiles, native contract, states, receipt/envelope identities and original as-of. Use `pair=PID` instead of `quote` for a pair and both original legs. Current Details is aged by its own dependencies, not automatically labeled historical because it has a result ID. |
| `/api/boards/inputs?game=KEY` | Full combined original input bundle, including exact immutable envelopes and source-local alternatives, without finance. Add `result_id=RID` to reopen the exact saved snapshot bundle after arrivals; Details returns its `original_inputs_identity`. At most 8 MiB. |
| `/api/boards/history?game=KEY` | Up to 50 immutable results for the selected policy, newest first, with result/snapshot IDs and original calculation timestamps. Exact older IDs remain reopenable through Details even after a member disappears. |

Pass canonical `game_key` from the catalog, URL encoded. A bounded exact source member `provider:native_event_id` also resolves to its occurrence for ordinary board requests. Saved Details/history use the canonical key and the exact policy variant. `result_id` must belong to that game and policy. Supplying both or neither `quote`/`pair` to Details refuses. `history=true` explicitly withdraws current ranking authority without rewriting saved bytes. Existing `/api/stored/games` and `/api/stored/result` and original source-local projections/readers remain available for compatibility.

Calculation queries accept exact decimal strings `amount` (default `1000`), `buffer` (rate, default `0.005`), `benchmark_venue` (`pinnacle`, `novig`, `prophetx`) and `benchmark_method=proportional_no_vig`. The compatible `ceiling` alias must equal `amount` if both appear. `sizing_mode=requested_trade` is ordinary; explicit `ceiling` mode retains the financial owner's separately identified historical-style comparison. The policy owner validates complete shapes/ranges and includes every setting in its revision. Unknown/duplicate query fields or oversized values reject; a missing selected benchmark remains missing, with no substitute.

`financial_metrics.net_modeled_ev_usd` and `buffered_ev_usd` are complete modeled EV. `conditional_net_ev_usd` and `conditional_buffered_ev_usd` remain separate when a complete probability partition is unknown. Percentage denominators are actual deployed funding. The API additionally formats exact conditional return percentages from the financial owner's exact dollar/funding values. No browser calculation of fees, allocation, rule effects or settlement is needed. The ambiguous predecessor top-level buffered-profit alias is omitted. Singles never establish an arb. All results keeps negative/conditional comparisons; default empty states never imply a positive opportunity.

The benchmark's fair probabilities concern decisive home/away wins. Common odds are a display conversion of the original offered price, not an assertion of identical exceptional payouts. Original native predicates, completion windows and quantity models remain authoritative. Actual fills, fees/charges and grades stay unknown; the named cent-contract grid is separate from observed depth. See [financial contract](requested-trade-financial-contract.md) and [combined-input contract](combined-occurrence-input-contract.md).

## Delivery and freshness

Every compact response includes `version`, `view`, `filter`, canonical `game_key`, `input_version`, exact `policy`, named `benchmark`, original `as_of`, `result_as_of`, `read_at`, `result_id`, `snapshot_id`, `delivery_state`, `status`, current original `prices`, chosen `rows`, `empty_reason` and explicit bounds. Financial rows carry immutable Details identity; prices carry `inputs_identity` with original envelope IDs. The compact and catalog caps are 512 KiB. Details/inputs retain full originals with an 8 MiB cap. [Board schema](contracts/predict-comparison-board-1.schema.json) and [catalog schema](contracts/predict-board-catalog-1.schema.json) are structural response contracts.

HTTP 200 means a complete saved variant is inspectable, or a stopped/history read is inspectable. It does not imply current or positive results. HTTP 202 means local calculation is pending: original prices remain present; if a prior result exists its original snapshot, result as-of and per-row freshness remain explicit. HTTP 409 identifies a bounded identity/capacity/selection refusal; 503 identifies database unavailability. Browser reads/settings do not call providers, migrate SQL, alter acquisition authority, activate recovery or touch accounting/holds.

Each single is checked against its original quote/receipt clocks, selected reference clocks, all attached profile expiries, exact content/match applicability and kickoff. Each pair takes only its two legs' dependency status. A stale alternative never globally marks the occurrence historical. `status=mixed` is expected for mixed-age inputs. A changed/removed member or benchmark revokes only comparisons whose exact original dependency fingerprints changed; unaffected prior comparisons can remain current while recalculation is pending. All original numbers remain inspectable. Stop/history withdraws every positive-list flag. Source time, receipt time, original evaluation as-of and model horizons never renew on reads or unchanged captures.

## Capture, calculation and latest ownership

1. Existing segmented-journal ingress persists immutable envelopes and admitted source projections through `GameStore.import_record`. The ingress/capture/publication owners share a transaction advisory lock, in addition to existing row CAS. Source clocks retain exact ordering. Older or equal-source arrivals do not overwrite admitted projections.
2. `GameStore.combined_capture` reads envelope associations in one SQL statement, bounded to 256 originals / 24 MiB and 8,192 associations. combined-input `build(..., associations=...)` consumes the exact admitted per-member association while retaining each full original envelope. Historical combined-input `build` without this optional argument remains unchanged. This avoids a whole retained envelope reintroducing a superseded member.
3. `storage.comparison_board.capture(store, game, policy, at=...)` resolves the selected occurrence, captures its source/member/binding guard, calls `retain_combined`, then the existing immutable `snapshot`. Benchmark-specific internal projection keys keep alternative benchmark variants independent. Unchanged source/binding/engine captures reuse the saved original as-of and snapshot. Policy amount/buffer variants get distinct snapshots/latest keys.
4. The capture transaction ends. Existing `storage.current_games.calculate(snapshot)` invokes shared financial owners outside capture locks. No new financial engine or database is introduced.
5. Existing `GameStore.publish` retains the immutable result, validates snapshot/game/input/policy/engine association, locks publication, and compares current source/member guard, projection input version and exact engine binding. A changed source, membership, binding, engine, retired settings generation or stopped worker refuses latest publication; the completed old result remains immutable history. No historical engine binding is rewritten.
6. `DatabasePipeline` keeps at most four coalesced pending requests; changing settings for the same game/benchmark replaces queued settings, while distinct benchmarks remain separately identified. It performs at most one selected/visible-game calculation per tick, imports at most 64 journal records within a one-second import budget, and never schedules the whole slate because another game arrived. The existing finite failure and owned-close behavior remains. Pending-generation identity is checked immediately before publication. Relevant arrivals are detected from admitted associations, including removal and occurrence membership changes.
